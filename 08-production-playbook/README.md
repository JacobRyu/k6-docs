# 08. 本番運用プレイブック

ここまでの章は「ツールの使い方」でした。この章は**組織で負荷試験を回し、リリース判断とキャパシティ計画に使う**ための進め方です。

> 負荷試験の失敗の多くは、ツールではなく**目的の曖昧さ**と**環境の違い**から来ます。

---

## 1. 全体プロセス

```
① 目的と合否基準を決める
        ↓
② ワークロードを設計する（誰が、どのくらい、どんな順番で）
        ↓
③ 環境とデータを整える（本番同等・安全）
        ↓
④ 実施する（段階的に、監視しながら）
        ↓
⑤ 分析する（クライアント + サーバー側）
        ↓
⑥ 報告し、判断する（リリース可否・改善項目）
        ↓
⑦ 定着させる（定期実行・SLO・キャパ計画）
```

各フェーズの成果物を残してください。特に ① と ⑥ が抜けると「数字だけ出て結論が出ない」会になります。

---

## 2. ① 目的と合否基準

### 悪い目的

- 「とりあえず負荷をかけてみる」
- 「何 RPS 出るか見たい」
- 「速いか確認したい」

### 良い目的（仮説の形にする）

| 目的 | 仮説 | 合否基準 |
| --- | --- | --- |
| リリース可否 | 新機能追加後もピーク帯で SLO を満たす | p95 < 800ms、エラー率 < 0.1% |
| キャパ計画 | 現構成でピークの 2 倍まで耐えられる | 2 倍負荷で p99 < 2s、エラー率 < 1% |
| ボトルネック特定 | DB コネクションが先に飽和する | 飽和点の特定と再現手順 |
| 回帰検知 | 前回リリースから性能劣化がない | p95 が前回比 +10% 以内 |
| 障害耐性 | 1 台停止しても SLO を維持 | 縮退運転で p95 < 1s |

**合否基準は数値で、測定方法もセットで**書きます。「p95 < 800ms（`http_req_duration`、10 分定常区間、シナリオ browse）」のように。

---

## 3. ② ワークロード設計

### 決めること

| 項目 | 例 | 根拠 |
| --- | --- | --- |
| ピーク同時接続 / RPS | 300 RPS | アクセスログの上位 1% 日 |
| シナリオ比率 | 閲覧 70%、検索 25%、購入 5% | 本番の行動ログ |
| 思考時間 | 2〜5 秒 | 実ユーザーの操作間隔 |
| データ量 | 本番同等（例: 100 万件） | インデックス・キャッシュの効き方が変わる |
| 試験時間 | 定常 20 分 + ramp | ウォームアップとリーク検知 |
| 成長率 | 半年で 2 倍 | 事業計画 |

### 負荷モデルの選び方

- **ユーザー数が本質**（Web/社内システム）→ 閉じたモデル（`ramping-vus`）
- **リクエスト量が本質**（API、他サービスからの呼び出し）→ 開いたモデル（`arrival-rate`）
- 両方ある → シナリオを分けて同時実行（第 3 章）

### 現実装の負荷を再現するコツ

- 主要エンドポイントだけでなく、**静的アセット・認証・検索**も含める
- 実際の遷移順（一覧 → 詳細 → カート）を再現する
- キャッシュヒット率が本番と揃うようにデータを用意する
- 外部 API はモック or サンドボックスを使い、**外部のレート制限**を踏まない

---

## 4. ③ 環境とデータ

### 本番同等性のチェック

| 観点 | 確認事項 |
| --- | --- |
| スペック | インスタンスタイプ、台数、オートスケール設定 |
| ネットワーク | LB、CDN、WAF、VPC 内通信、レイテンシ |
| データ | 件数、分布、インデックス、統計情報 |
| キャッシュ | Redis/CDN の状態、ヒット率 |
| 外部依存 | 決済、メール、認証基盤（モック/サンドボックス） |
| 監視 | APM、ログ、DB メトリクスが取れている |
| その他 | 同時に走るバッチ、CI、他チームの試験 |

**staging が本番より小さければ、結果は「下限」として扱う**。絶対値ではなく傾向とボトルネックを見ます。

### データの安全性

- 本番データをコピーしない（個人情報・容量・整合性）
- 専用テナント / 専用アカウント / 専用 DB スキーマ
- 書き込みは TTL 付き、または試験後に一括削除
- 外部にメール・SMS・決済を飛ばさない（サンドボックス or モック）

---

## 5. 本番環境で実施する場合のガードレール

本番でしか再現できない事情（データ量、ネットワーク、実構成）がある場合の必須事項です。

| ガードレール | 具体策 |
| --- | --- |
| 書き込み禁止 | 参照系のみ、または専用テナントに限定 |
| 専用アカウント | 最小権限、レート制限の対象外設定を確認 |
| 自動停止 | `abortOnFail` + `delayAbortEval` |
| 段階的負荷 | 10% → 25% → 50% → 100%。各段階で判断 |
| キルスイッチ | 実行担当が即座に Ctrl-C できる体制。CI なら cancel |
| 監視 | エラー率、レイテンシ、CPU、DB、キュー、外部依存 |
| 連絡 | 事前にステークホルダーへ周知。オンコールと共有 |
| 時間帯 | ピークを外す。ただし「ピーク帯の検証」が目的なら合意の上で |
| ロールバック | 問題時の切り戻し手順を用意 |
| 法令・契約 | 可用性 SLA への影響、顧客への通知要否を確認 |

> 「本番で負荷試験をしてよいか」は技術判断ではなく**事業判断**です。承認を記録に残してください。

## 6. ④ 実施

### タイムライン（例）

| タイミング | 作業 |
| --- | --- |
| 1 週間前 | 計画書承認、環境準備、データ投入、スモーク実施 |
| 前日 | 監視ダッシュボード確認、連絡、ロールバック手順確認 |
| 30 分前 | ベースライン計測（負荷なし）、ウォームアップ |
| 実施中 | 段階的に負荷を上げ、各段階で 5 分観察。異常時は即中止 |
| 終了後 | 負荷停止を確認、データ後始末、初期結果の共有 |
| 翌日 | 分析、報告書、改善チケット |

### 実施中に見るもの

- k6 側: `http_req_failed`、`http_req_duration` p95/p99、`dropped_iterations`、VU 数
- サーバー側: CPU、メモリ、GC、DB 接続数/スロークエリ、キュー長、外部 API レイテンシ
- 事業側: エラー通知、サポート問い合わせ、決済成功率

**「k6 の数字が良い = サービスが良い」ではありません。** サーバー側が飽和していれば、次の負荷で折れます。

### 中止条件（事前に決める）

- エラー率が X% を超えた
- p99 が Y 秒を超えた
- DB の接続数が上限の 80% に達した
- 外部依存でエラーが発生した
- オンコールから停止要請があった

## 7. ⑤ 分析

### 飽和曲線を描く

負荷（RPS または VU）を横軸、レイテンシとエラー率を縦軸に取ります。

```
レイテンシ
  │                        ╱ ← 飽和点以降は急上昇
  │                   ╱
  │              ╱
  │         ╱
  └──────────────────────── 負荷
```

- 線形に増えている範囲 = 余裕のある領域
- 曲がり始めた点 = **実用的な上限**
- 急上昇 + エラー = 飽和

### ボトルネックの切り分け

| 観測 | 疑う場所 | 確認方法 |
| --- | --- | --- |
| `http_req_waiting` が遅い | AP / DB / 外部 API | APM のトレース、スロークエリログ |
| `http_req_connecting` が遅い | DNS / LB / ネットワーク | DNS 解決時間、LB のメトリクス |
| `http_req_blocked` が遅い | コネクションプール | k6 の接続再利用設定、サーバーの keep-alive |
| 特定エンドポイントだけ遅い | クエリ / N+1 / ロック | 該当 API のトレース |
| 時間とともに悪化 | メモリリーク / コネクション枯渇 | 長時間のメモリ・FD 数 |
| エラーが 429 | レート制限 / WAF | 該当レイヤの設定 |
| k6 の CPU が 100% | 試験ツール側の限界 | VU 削減、`discardResponseBodies`、分散 |

### 誤検知のパターン

- **ウォームアップを含めて判定**している → 定常区間だけ見る
- **キャッシュが温まっていない** → 事前にウォームアップ
- **同時に他のジョブが動いていた** → 実行カレンダーで排他
- **データ量が本番と違う** → 傾向のみを評価
- **外部 API のレート制限** → モック化
- **k6 側のリソース不足** → `dropped_iterations` と CPU を確認

## 8. ⑥ 報告と判断

報告書の型は [`templates/report.md`](templates/report.md)、計画書は [`templates/test-plan.md`](templates/test-plan.md)。

**必ず「判断」を書く**:

- リリース可 / 不可 / 条件付き可
- 改善が必要な項目と優先度
- 再試験の条件（いつ、何を変えたら）
- 残存リスク（例: ピーク 3 倍は未検証）

数字だけ並んだ報告書は、次の意思決定に使えません。

## 9. ⑦ 定着させる

### 定期試験のカレンダー

| 頻度 | 内容 | 目的 |
| --- | --- | --- |
| 毎 PR | スモーク（1〜3 分） | 壊れていないか |
| 毎晩 | ロード（10〜30 分） | 回帰検知 |
| 毎週 | ソーク（2〜4 時間） | リーク・枯渇 |
| 毎月/リリース前 | ストレス / スパイク | 限界と回復力 |
| 四半期 | キャパシティレビュー | 成長に対する余裕 |

### SLO とダッシュボード

- SLI を k6 のメトリクスと対応させる（エラー率 = `http_req_failed`、レイテンシ = `http_req_duration`）
- しきい値を SLO から逆算する（第 5 章）
- 試験結果を時系列で並べ、トレンドを見る（Prometheus / Grafana）
- 劣化を検知したら自動でチケットを作る

### キャパシティ計画

```
必要台数 ≒ ピーク RPS ÷ 1 台あたりの処理可能 RPS × 安全率(1.5〜2.0)
```

1 台あたりの限界は、**飽和曲線の曲がり始め**から求めます。平均値ではなく p95/p99 が SLO を超える点を基準に。

## 10. アンチパターン

| アンチパターン | 何が起きるか | 対策 |
| --- | --- | --- |
| 目的なしで負荷をかける | 数字は出るが判断できない | 仮説と合否基準を先に書く |
| 平均値で判断 | テールの遅さを見逃す | p95/p99 |
| しきい値なし | 目視運用になり形骸化 | thresholds + exit code |
| 1 シナリオだけ | 実際の混在負荷と違う | 複数シナリオ |
| 本番データをそのまま使う | 情報漏えい・容量問題 | 生成データ / 匿名化 |
| 本番で無制限に負荷 | 障害・SLA 違反 | ガードレール、段階的 |
| 結果を保存しない | 再現・比較できない | スクリプト+設定+結果をセット保存 |
| サーバー側を見ない | ボトルネックが分からない | APM/DB/CPU と突き合わせ |
| 一度やって終わり | 劣化に気づけない | CI/定期実行 |
| k6 の限界を無視 | ツール側がボトルネック | `dropped_iterations` と CPU 監視 |

## 11. k6 OSS と Grafana Cloud k6

| 観点 | OSS | Cloud |
| --- | --- | --- |
| コスト | 無料 | 従量/契約 |
| 分散実行 | Operator 等を自前運用 | マネージド |
| 結果保存 | 自前（Prometheus 等） | 標準搭載 |
| チーム共有 | 自前 | URL 共有・比較 |
| 地理分散 | 自前 | リージョン選択 |
| データ所在地 | 自管理 | 要確認 |
| 向く組織 | 内製・k8s がある | 運用を任せたい |

## 12. 成熟度モデル

| Lv | 状態 | 次の一歩 |
| --- | --- | --- |
| 1 | 手動で 1 回だけ実施 | しきい値とレポートを整備 |
| 2 | リリース前に実施、合否あり | CI にスモークを追加 |
| 3 | PR でスモーク、夜間でロード | 結果の時系列保存、回帰検知 |
| 4 | SLO と連動、キャパ計画に活用 | 障害試験・カオスとの統合 |

## 13. 最終チェックリスト

**計画**
- [ ] 目的が仮説の形になっている
- [ ] 合否基準が数値と測定方法で定義されている
- [ ] ピーク値の根拠がある
- [ ] 本番実施の承認を得た（該当する場合）

**環境**
- [ ] 本番同等性を確認した（差分は記録した）
- [ ] データ量・分布が現実的
- [ ] 外部依存がモック/サンドボックス
- [ ] 監視が有効

**安全**
- [ ] `abortOnFail` を設定した
- [ ] 中止条件とキルスイッチを共有した
- [ ] 書き込み系の影響範囲を限定した
- [ ] 後始末の方法を決めた

**実施**
- [ ] スモーク → ロード → ストレスの順で進めた
- [ ] ウォームアップと判定区間を分けた
- [ ] `dropped_iterations` を確認した
- [ ] サーバー側メトリクスを同時に取得した

**報告**
- [ ] しきい値の合否が明記されている
- [ ] ボトルネックと根拠がある
- [ ] 判断（可/不可/条件付き）がある
- [ ] 再試験の条件がある
- [ ] 成果物が保存されている
